    SetValue




    **************************

    *** When to call *** 1 ***

    **************************
    (Kent Sandvik) wrote:
    If you don't need to refresh the view a simple
    frameName.slot[index] := value
    I know, it looks bad to disagree on the net, but it's not true that SetValue should only be used when the interface needs to refresh. Using SetValue instead of direct manipulation gives the view a chance to respond to the change and update *any* internal or dependent data. Since you can't always guarantee that you know about the underlying implementation, you should always use SetValue when changing values in foreign views.
    --Bob

    **************************

    with SetValue leaves the display unchanged (until some stroke is made in
    the view).
    You may need to explicitly call RefreshViews() to get the display to update, depending on when/how you call SetValue.

    *** When to call *** 3 ***

    **************************
    Blair MacIntyre wrote:
    When I change a 'text slot, I always just assign the text slot and call
    Dirty() on the view.
    This will not work reliably.
    You really need to use SetValue - setting the slot directly, followed by a call to dirty is NOT equivalent. You can get away with sometimes and for some slots, but this no guarantee your code will continue to work in the future. I see a lot of people doing this, I'm not sure where the origin of this misinformation is.
    The basic issue is that the view system doesn't continually examine the slots in a view - it caches some of this info. Dirty doesn't force the caches to be updated from the slots. Text slots are one of these cases where the view system caches the value of the text slot. I don't have a list of which slots are cached and which aren't. Such a list wouldn't be particularly useful as things may change in the future.
    The only time you don't need to use SetValue is in your ViewSetupFormScript. At this point - you're view doesn't really exist yet. As it's created all the slots are examined.

    Path expression



    > SetValue(viewname, 'framename.slot[index], value);
    > This didn't work...
    The reason your SetValue call didn't work is because 'frameName.slot[index] is not a valid path expression. A valid path expression for what I think you're trying to do would be [path: 'frameName, 'slot, index]. (You cannot include array indexes in the dot notation form of path expressions.) See the NewtonScript Reference Manual for details.

    Overriding System messages


    When overriding system messages, make sure to call the inherited method. Even if the message isn't handled by the current prototype, it may be on a future Newton or even on current ones due to patches, so it's safest to call the inherited one. The :? calling syntax doesn't throw an exception if the inherited method doesn't exist (as the regular : calling syntax would).

    BuildContext


    Jerry Goldstein wrote:
    Thanks for the reply. I read the stuff on BuildContext, but I'm not sure how
    to implement it in conjuction with what you suggested above. Can you give me
    a short example?
    Checkout the "Tales From the View System" article. Also the UpInSmoke sample code gives a short (really short) example.
    Basically, you pass BuildContext a template (probably a user proto you defined in NTK, PT_). Save the result - that's your view. Send it an Open message and then a Show message. I think the trick here is that you need to make sure the template does NOT have the visible bit set - else when you send the show message the views system thinks the view is already shown and does nothing.     Sample
    ******
    local danQuayle := BuildContext({viewClass:clView, viewFlags:vFloating, viewBounds:smokeBounds}); danQuayle:Open(); danQuayle:Close();
    BuildContext takes a template as an argument and returns the view it constructed from that template. The views parent is the root view. The template is not added to the root views viewChildren arrayyou can liken the view to a free agent. BuildContext should not be treated as a general purpose method for creating views dynamically. Its only useful in special situations like the one at hand. The template passed to BuildContext is the bare minimum amount of information you need to create a view. The only part worth discussing is the viewFlags. If vFloating isnt specified, the dummy view appears behind any floating views that happen to be around. Hence, those floating views wouldnt be forced to update when the dummy view is closed."

    Memory Leaks


    In article , sandeep@mv.mv.com (Sandeep Shah) wrote:
    In an effort to conserve the precious heap space, I have reworked my app
    a few times, until I have hit the wall. What happens is this: After a
    while I seem to be using inordinately high amount of memory (~30K) which
    I can't account to what I am doing in the app. I carefully nil out
    all largish arrays, etc. Even after I close my app the memory is not
    reclaimed. (I keep minimal state ~500 bytes)
    There are other places an app can "leak" besides the base view. What sorts of things is the app doing? Is it registering with Intelligent Assistance and not unregistering? Is it adding largish undo actions and not calling ClearUndoStacks()? Is it creating custom dictionaries that are not deallocated? Is it creating views with BuildContext that are not closed?
    Sadly, there's no easy way to track down such allocations. Clearing out the slots in you base view will get just about everything that's accessed "normally" from your app. (BTW--just set the slots to NIL, don't bother with RemoveSlot.)
    To find the rest of the leaks, you'll pretty much have to bite the bullet and look through your code for calls that might register things with the system. Try to get a good feel for when the space is leaked. (e.g. open/close, install/remove, doing a find, etc.)
    --Bob Bob Ebert, Developer Technical Support, PIE Division, Apple Computer Inc.

    Faking Case Statements


    Frames can simulate case statements on symbols or string values (I don't know of any lang that lets you case on strings)
    f := { foo: func() Print(1), bar: func() Print(2), dog: func() Print(3), |the quick|: func() Print(4), };
    Perform(f,Intern("the quick"),[]); 4 #2 NIL
    If you are casing on a dense range of ordinal values you can use an array of closures:
    a:=[func() Print(0),func() Print(1),func() Print(2)];
    call a[Ord($b) - Ord($a)] with (); 1 #2 NIL
    If it's not a dense range you'll want to either convert your ints to strings and use the frame method or do binary search on an array of possible values.
    I'd do some testing to see when these techniques actually pay off.

    Parameter passing


    In article <2k4h42$al1@apple.com> engber@apple.com (Mike Engber) writes:
    A litmus test (semi-language independant*):
    function(x) begin x:=12; end;
    Will this function make a change that affects the parameter it's passed?
    Yes -> call by reference
    No -> call by value

    -ME

    *Technically, there are some other esoteric parameter passing
    mechanisms that will mess up this test. I don't have the Red Dragon
    book handy at the moment. But, if we confine ourselves to C, C++,
    Pascal, LISP, Fortran, and NS - this test holds water.
    Isn't ALGOL-60 fun? I've always "thunk" so.
    The real point here is that to successfully program in NS, you have to indulge in those dirty little daydreams about how it might be implemented.
    Technically, Newtonscript parameters are passed by value, but most things of interest are objects, and they are never passed. Only references to them are passed. YES, the reference is passed by value, but to harp on that is confusing.
    Stop to think how this is implemented. Frames are not going to be stuffed onto the stack, a pointer to them is going to be put there instead. Now review all the data types in Newtonscript and understand which are immediate (passed by value) and which are objects (sho act like "pass by reference").
    Everywhere in NS you have to always remember what is a simple datum, and what is a big, bad, wonderful, expensive ("don't try pointer equivalency if you don't mean it") object.

    call func() begin local f := {}; local fn := func() begin local s,v; foreach s,v in f do write(s); write($\n); end;

    Send Request Limitations with the Comms Architecture (2/21/94)
    Each send request (using Output or OutputFrame) is queued in the underlying comms architecture. In the case of serial and modem options, the current comms architecture allocates data structures up to five send requests, in the case of ADSP options up to three. This means that you can't do more than five respective three outputs without blocking.

    Q&A: Abort Calls When you issue an Abort message to the endpoint, the endpoint will get tid of any pending I/O calls. However. this might happen some time after the Abort call has been issued.
    What to do? Well, you have to wait a certain time period, and continue with possible Disconnect and Dispose calls.
    You can't tear down the endpoint until all I/O has completed. The communication system automatically requeues an asynch receive every time a receive completes. To prevent this automatic behavior, you must set the nextInputSpec to nil after completing the last input in the application.
    If you are attempting to tear down a session while an inputSpec is active, you must call :SetInputSpec(nil), AND CLEAR THE nextInputSpec SLOT before calling Abort.
    Note that calling SetInputSpec(nil) does not cancel the outstanding receive, so you must still call Abort and delay so the cancelled receive has a chance to complete.
    Here's an example of how to use AddDelayedAction as part of the disconnect and termination of the endpoint:
    endPoint.nextInputSpec := nil; // Need to clear both // inputSpec slots! // note that the ordering is important, you need to set the // nextInputSpec to nil before the current one to nil!
    endPoint:SetInputSpec(nil); // Need to clear both // inputSpec slots! endPoint:Abort(); // Call Abort, then make a delayed action that // will continue with the process 1000ms later: AddDelayedAction(func() begin endPoint:Disconnect(); endPoint:Dispose(); end, [],1000);
    Abort does not really abort. The problem is that if there is an input spec pending, Abort can't terminate it. The Abort completes, and the input spec is requeued. In order to prevent this, you must make sure that there is no input spec pending.
    You would think you could do this by just calling SetInputSpec(nil). Unfortunately, this just tells the toolbox to stop servicing the current input spec, and move on to the next one specified by the nextInputSpec slot. This means that calling SetInputSpec(nil) just moves to the next one in the chain. If you really want to cancel the input spec, you must clear the nextInputSpec slot FIRST, before calling SetInputSpec. This way, when SetInputSpec is called there is no next input spec to go to. After this, it is finally safe to call Abort, and you will get the desired results. Phew!

    Traversing a soup entry


    In article <2ja8dg$jdu@scratchy.reed.edu>, P. Douglas Reeder wrote:
    Is there a way to test for deep equality? I.e. to test that the
    contents of two frames or arrays are the same, though some pointers
    may be different?
    I don't think there is a function like that built into NewtonScript. However, it wouldn't be too hard to write. To get you started, I've enclosed a function that traverses a soup entry and calls a closure on each object in the entry. Note that soup entries are really cyclic graphs, so you can't just do a tree walk on them (you would end up in infinite regress); hence I keep track of where I've been in a NewtonScript array. This probably isn't the most efficient way of coding it, so don't go putting this into you inner loops :-), but...
    TraverseSoupEntry := func(entry, keysToIgnore, closure) begin local IsFrameOrArray := func(object) begin (PrimClassOf(object) = 'frame) or (PrimClassOf(object) = 'array); end; local visitedObjects := []; local visited := func(obj) ArrayPos(visitedObjects, obj, 0, nil); local visit := func(obj) begin AddArraySlot(visitedObjects, obj); // this calls closure on interior nodes of graph call closure with (obj); end; local traverse := func (obj) begin if (call isFrameOrArray with (obj)) then begin if not(call visited with (obj)) then begin call visit with (obj); foreach key, value in obj do if not(ArrayPos(keysToIgnore, key, 0, nil)) then begin call traverse with (value); end end; end else // this calls closure on exterior nodes of graph call closure with (obj); end; call traverse with (entry); end;

    I use it to insert an item, "Print Envelope" after the 'Print ("PrintCard") item in the cardFile's routing entry. The cool thing about a function like this is it's size independent or size dependent depending on how you want it.
    The parameters are
    newFrame := InsertSlot(frame, slotAfterSymbol, slotSymbol, slotContents);
    frame = the frame you want to insert into slotAfterSymbol = misleading name. It can be a symbol ('Print), a item number, or nil. If you supply a symbol, it will insert your slot after that symbol. If you supply a number, it will insert your item after that nth slot, and if you supply nil, it will insert your slot at the top of the frame. Therefore, if you want to append something to the frame, you could do InsertSlot(frame, Length(frame) - 1, 'Moof, { Hi: 'moo }) or just say frame.Moof := { Hi: 'moo } since it seems that items are usually appended to frames.

    String rewriting?


    Last night for kicks i was reading Przemyslaw Prusinkiewicz and Aristid Lindenmayer, _The_Algorithmic_Beauty_of_Plants_, and on page 3, they talk about the most basic form of a DOL-system, a deterministic, context-free system for rewriting strings.
    Suppose we have axiom: "b" and rewriting rules: rule 1: "a" -> "a" "b" rule 2: "b" -> a
    such that applying the rules to the axiom multiple times yields something like this:
    1: "a" 2: "a" "b" 3: "a" "b" "a" 4: "a" "b" "a" "a" "b" 5: "a" "b" "a" "a" "b" "a" "b" "a" 6: "a" "b" "a" "a" "b" "a" "b" "a" "a" "b" "a" "a" "b" and so on...
    So, in NTK, build some slots:
    depth: 6
    turtleAxiom: ["b"] // an array with one element
    turtleRules: {rule1: {original: "a", production: ["a", "b"]}, rule2: {original: "b", "production: ["a"]}}
    turtleInstructions: nil
    begin local count turtleInstructions := clone(turtleAxiom) // start with the axiom buildRule:= []; // temporary storage for each pass for count:= 1 to depth do // # of times to apply the rules begin forEach instruction in turtleInstructions do if StrEqual (instruction, rule.original) then forEach element in rule.production do Add ArraySlot(buildRule, element); turtleInstructions:=clone(buildRule); print(turtleInstructions); buildRule := []; end; end

    NewtonScript character set


    When converting strings to symbols and vice versa, keep in mind that the character sets of strings and symbols are not the same. Strings use 16-bit Unicode characters, but symbols use 7-bit ASCII. So, for example, if your program is running on a hypothetical Thai Newton and you try to convert some Thai text to a symbol, you will get something unpleasant.
    By the way, 8-bit characters may seem to work in symbols, but they aren't part of the "official" definition of NewtonScript, and their translation may vary on different compilers. This applies to using Mac extended characters in strings as well: it's safest to use \u for special characters.

    Auto parts


    Hi all,
    I've been talking directly to some folks at PIE for a while about auto parts. If you're interested in using them, read Mike Engber's article, "Bit Parts", send me some mail, read some of the posts I'm going to make about them.
    They're pretty simple to create. You MUST have NTK 1.01 or greater. NOTHING earlier will support them.
    Reading "Bit Parts" will save me a lot of set up, go get it and read it.
    What you have to do to create one:
    Go to Project/Settings... and set:
    Name: auto Symbol: auto
    Name: yourPackage:yourSignature
    The names and Symbol up top MUST be set to 'auto'. This is how NTK recognizes not to create a regular package, but an auto part.
    The Name at the middle is the appSymbol the package will use. Set this as per normal PIE guidelines.
    An auto part creates a package with 5 things:
    devInstallScript devRemoveScript InstallScript RemoveScript partData
    Of the five, you can alter the last three; Install, Remove and partData. Understanding partData is the key to understanding auto parts.
    You may not realize this, but NTK has the ability to take instructions from your code and execute it before it actually hits the Newton. You can assemble variables and such during the compile. This is accomplished in several ways, but where we need it is in what's called and afterScript.
    The afterScript is called when a view has been compiled. afterScripts DON'T get sent to the Newton, they're only executed at compile time. These are the auto parts key if I've not made it clear!
    To put something into an auto part, you need to create it and add it to the partData frame. This partData frame will get compiled into the package and will get passed to the Newton. This is where you need to put templates of views and everything you want from your code.
    How to do this? AFTERSCRIPTS!
    When a template get's compiled, one of the last things it does before being written in a package is execute it's afterScript. While in this afterScript, the just compiled view is available in a variable call 'thisView'. So in your afterscript you can use the contents of 'thisView'. This is not completely clear in Mike's article or the new docs. When you read it, you might get the impression that the 'thisView' text is being used as a pseudo slot or something, well, it's NOT. It's a real slot that's only 'there' during compile time.
    So, you can take the complete contents of a view after it's compiled and put it somewhere.
    This is the key. In your afterScript,do something like this:
    afterScript begin partData.myView :=3D thisView; end;
    NOTE: this is a codeblock, NOT a function, NO func() at the beginning here! This is a single Evaluate slot in the top level of you view.
    This now takes the compiled contents of your view and adds it as a frame in the compiler-time global partData. This is how you get a graphically-created NTK view into an auto part. You take it just after it's compiled and hang on to it in a frame that will get added to the actual package.
    =46ollowing me so far?
    Now that you've done this, how to use it?
    Well the partData frame can contain quite a bit of info. You can afterScript as much or as little as you want onto partData. Just use new slots 'inside' of partData. As in:
    partData.myView partData.myWiggyStuff partData.myOtherView
    So, now it's in the package and can be downloaded to the Newton. How do I 'get' access to the stuff from elsewhere? This is a bit harder.
    The frame partFrame, passed to the auto part during it's InstallScript is important. Anything you've tacked on to partData is passed to your packages' InstallScript. So all the above examples become:
    partFrame.partData.myView partFrame.partData.myWiggyStuff partFrame.partData.myOtherView
    while in the InstallScript. Now are you getting it? You could do something here, but DON'T just yet.
    In order to use the stuff from this frame you need to hang on to a reference to it AFTER it's InstallScript runs. You probably want to create a slot in the GetRoot() to point to it. This is a little hard to fully explain, but you want a POINTER to the data, NOT the data itself! The frame is in package space and can be referenced from there on demand. This is a bit of black magic the Newton does for you. This is perhaps why a lot of packages out there are causing memory problems. They don't know they don't have to clone the daylights out of everything all the time.
    Well, I'll go back on that tangent in another message. Suffice to say, you can take a clone of the partFrame slots and put it in the GetRoot().
    Do something like this during your InstallScript
    removeFrame.(EnsureInternal('myRemoveSlot)):=3D GetRoot().(EnsureInternal(kAppSymbol)).clone(partFrame.partData.myView);
    Whoa! That's a mouthful, eh? I'm really letting you in on some pretty cryptic stuff here. The above script does a lot more than you think. It create a slot in getRoot() that matches your kAppSymbol constant. You are using DefConst's, aren't you? Go back and read the samples if you're not.
    Then it makes that slot point to a clone of the partFrame.partData.myView slot. It's important to be careful how much you put in the top level of this view. Clone only makes a copy of the top level of an item. THIS IS IMPORTANT to save frame heap space. You can put something huge in this frame and this will destroy the heap. But, if you put the big stuff in a slot inside of this frame, it'll stay in the PACKAGE not in the root! I can't really explain this all here, just go with me on this...
    Now, what about the rest of the code? This is how you prevent the 'dreaded grip o' death'=81 when you create this stuff.
    Understand this, it's important.
    A variable can be internal or not. A variable's NAME can be internal or not. Go it yet? This is why you get the 'grip'. You're data is GONE when the card's ejected. If you just used:
    GetRoot().(kAppSymbol):=3DpartFrame.partData.myView
    there's a good chance the name of the getRoot() slot itself would be external and cause the 'grip'. Understand? I'll explain this in greater detail if everyone get's lost.
    So that's it! But what's the removeFrame stuff? Well, if you want to remove something after it's gone, you need to know where its located. This removeFrame is passed to the removeScript your package executes AFTER a card eject. Since you're creating something in the GetRoot(), you'll want to remove it. However, you can't 'see' it unless you've hung on to a reference to it. This is why it's added to the removeFrame.
    You can then use it in your RemoveScript:
    RemoveSlot(GetRoot(), removeFrame.myRemoveSlot);
    This takes the actual reference to the slot from when it got created. You don't have to do this for a GetRoot() frame since you may actually know the name of the slot. In that case you could decide not to hang onto the slot in the removeFrame and just remove it like so:
    RemoveSlot(GetRoot(), (kAppSymbol))
    But this is NOT what you want in other cases. A prize to the first person who mails me with an example of when you'd HAVE to use the removeFrame...
    So,that's the story behind auto parts.
    If you want to get a graphic view to a part, use afterScript to add it to partData If you want to use it from elsewhere, use installScript to add a reference= to it If you want to remove it, hang on to a ref to it and add that to the removeF= rame
    Go it? Want a sample? Check out my SleepSoundPro Sound Packages. There's source to it on the uiowa server.

    Dictionary stuff


    Stephen D. Cohen wrote:
    Has anyone successfully stored a custom dictionary in a soup?
    When I use GetDictionaryData, it returns a type that soup:Add()
    doesn't like (binary data instead of a frame). Any ideas around this?
    Did you pass the binary data directly to Add? OR Did you make a frame and put the binary data in a slot of the frame. You can only pass frames to Add - or AddToDefaultStore.
    Also, have you considered how you'll get your dictionary soup to your users? Unless you're shipping on PCMCIA cards this is not straightforward.
    I suggest an considering an entirely different approach.
    It may be more efficient and convenient to just to keep your base dictionary data right in your package. You may also get better compression. Of course the dictionary data will be read-only.
    If you're planning to allow users to make additions - you'll have to store those additions in a soup. I'd suggest using a separate dictionary that's user modifiable and keeping just the user dictionary data in a soup.
    It may not be obvious how to accomplish getting dictionary data (or any binary object) into your package, so ...
    Use the NTK Listener to: - create your dictionary - which presumably you've already figured out how to do. - define the fn HexDumpBinObj - source below - call HexDumpBinObj on your dictionary - grab the hex that gets spit out to the Inspector - i.e. your dictionary - paste the hex into a rsrc using ResEdit's hex editor. e.g. create a new rsrc of type 'dict' and edit it. Give it the name "myDictionary". - use GetNamedResource in ProjectData to retrieve your dictionary at build time. e.g. refNum := OpenResFileX(Home & "SomeProject.rsrc"); gMyDict := GetNamedResource("dict","myDictionary",'dictdata); CloseResFileX(refNum); - use gMyDict to initialize an evaluate slot in your base view. You can access this slot at run-time to get your dictionary.
    func HexDumpBinObj(binaryObj) begin local i; constant kHexDigits := "0123456789ABCDEF"; for i := 0 to Length(binaryObj)-1 do begin local byte := ExtractByte(binaryObj,i); Write(kHexDigits[byte >> 4]); Write(kHexDigits[band(byte,0x0F)]); end; Write($\n); end
    An example call:
    GenBinaryDataString(GetDictionaryData(33),'dictdata) ->61076170627063706470657066706770687...
    Of course, you'll use your dictionary instead of dictionary 33 (the letters dictionary).

    nice in your replies. :-)

    In article <2gpfip$27d@news1.digex.net> wkearney@access.digex.net (William Kearney) writes:
    Maybe it's just my hangover from last night, but I'm having a difficult
    time dealing with path expressions.
    Look at path expressions from the perspective of a routine that needs to know "What slot should I use?".
    Say you are going to be passed in a bunch of frames and you are going to sort them. The frames will come in as an array and go out as an array. Cool. Next problem is "What do I sort on?" Seems that using one of the slots would be a good idea.
    OK, so another parameter is the slot on which to sort.
    sortedArray := FrameSorter(unsortedArray, theSlot)
    That is sort of a prototype for the function.
    The next question is what goes in the "theSlot" parameter? Ready? A "path expression"!
    Think about it, you don't want the value of some slot, you want the name of the slot itself (which maybe has a different value in each frame). The FrameSorter will look up the slot contents. But you have to have a way to refer to a slot's name and not the slot contents.
    birthdayCardArray := FrameSorter(relatives, 'birthday);
    So what is with this single quote stuff? Welcome to the land of dynamic languages. In most languages--that is, static languages--symbols are something you use to name things like variables and functions, but it is part of the job of the compiler and linker to get rid of all these symbols before you run the program. By the time you are running your code the only symbols left are for debugging--if that.
    Dynamic languages don't forget all the names you use for things--after all, how could you add a slot while running your code if the language didn't keep track of the symbols used to name them?
    Symbols are another data type for Newtonscript. Apple might have called them "names", but they stuck with the computer tradition and did not make up a new term. (What do you think this is, Hypercard?)
    There you sit, drinking, having a good time. Across the table is your good friend Silvester. Suddenly you are overcome with what a silly name that is and blurt out: (quiz time)
    1) "Silvester is really stupid!" or 2) "The name Silvester is really stupid!"
    If you are about to lose a friend and possibly get beat up it is very important to appreciate the difference between the two statements.
    In pseudo-something these might be written:
    1) Stupid(Silvester) == sureThing 2) Stupid('Silvester) == sureThing
    Does that make path expressions a little clearer?
    Oh, and another thing, the "path" can be longer than a single symbol, it can even be an array listing a bunch of symbols:
    '[pathExpr: foo, bar, baz]
    Check out Newtonscript Reference 1-10, do some playing in the inspector, think about it.

    Print Formats


    Q: In my application I have two main print formats, but only one is really valid at any time. Can I change the default print format during the application runtime without getting into trouble?
    A: Every time the user opens the printSlip (or faxSlip) the system will check a slot in your application to see what format is the default one. You set the lastFormat slot to be the symbol that corresponds to the format you want to be the default choice.
    NOTE: If the user chooses a different slip, the lastFormat slot will be set accordingly. The lastFormat slot exists in your application base view, in other words the one attached to the root View.
    Note also that changing the default format in your setupRoutingSlip method will not have the desired effect, because the print (or fax) slip is already shown at this point of time. You have to set this up before setupRoutingSlip time, perhaps in reaction to some event in your application.
    NOTE: Mail uses a slot called lastMailFormat not lastFormat

    Some tips


    [Note: I am not speaking for Apple. I do not work in the Newton group.]
    I have noticed that a lot of the PD/Shareware/Commercial applications for the Newton suffer the following ailments:
    * They're big * They're slow * They're ugly
    This is not a fit of arrogance, but rather some suggestions in developing Newton software that will make things nicer for you (the smaller/nicer/faster your app is, the more people will love you). Take this as you will.
    1. Variable names are preserved in the package, and add to package size and probably code execution. How do I know this? Take a look with ViewFrame at the CodeBlocks you create in your package.
    The solution is simple, but lessens code clarity/readability, and sucks if you, like me, enjoy variables like "myNameSoupReference."
    Use variables like "i" or "ns" and such. It sucks, yes, but it will reduce your package size and make people happier since right now, memory and speed are at a premium.
    It would be *really nice* if Apple had a "feature" in a "noDebug" package build that would try to allocate 1 and 2 character symbols for your variables. This would be a very simple way to optimize. These symbols would "go away" if you were doing a Debug build or a "non-optimized" build.
    2. Don't keep stuff around in ram too long. Soup entries, tons of views (stepChildren, etc.). When in doubt, make the user wait a short instant and get the next 'n' soup entries rather than building dynamic views for all the entries in a soup. I did this at first in my forthcoming Envelopes application; bad thing to do, and you run into memory/view system problems with too many views or soup references.
    3. Try to "factor out" your code into proto's where applicable. If you use the same type of view for a dialog box 20 times in your application, make it a proto. If you don't like the way NTK does protos with userProtos, dump a userProto to a text file and paste the contents into a slot somewhere and use it as the value for a _proto slot somewhere. Redundant code only ups your package size.
    4. Don't paste in graphics that are from the Macintosh user interface. The Macintosh is a nice machine (I love it), but the Newton is not a Macintosh. If there is ever a Windoze NTK, don't do the same for Windoze.
    5. Don't use tons of huge PICTs in your packages. If you wonder why your package is so big, look in your resource files first. Don't draw a black or a dotted line in HyperCard and paste it in as a PICT; draw it from your viewDrawScript. Saves time, package size, etc.
    6. Whenever possible, use the built-in fonts instead of pasting in PICTs with lots of black pixels. Compression wants to preserve the black pixels, and the outcome of compression is usually somehow related to how many black areas you have in your pictures.
    7. Use buttons that are the standard size - don't make your buttons to high, and don't make them too short - give some white space "breathing room" between the text and the edge of the button.
    8. Don't do lots of nasty processing as the first thing when a user opens your application. It makes the Newton feel like a zoomer. Instead, let your initial view open to display *something* and then do any processing. Gives the appearance that your app is zippier and more responsive.
    9. Don't over-use sounds in your application, especially sounds like the drawer opening and closing and such, and especially sounds where they will annoy the user or are unnecessary. And don't use really big sounds at the highest sampling rate in your packages.
    10. Never have a blank view open and wait for processing to display something in it. Never have a button hilited seeminly forever when processing is going on, and then have something happen.
    11. After a frequently seen view is opened, when it's 'closed', hide it and show it later rather than open/close, unless the view has lots of slots in it that have lots of data in them, in which case make an educated decision about what to do. Open/Close takes a lot longer than show/hide.
    12. Make elegant use of LockScreen.
    These are just a few things I've noticed in programming Newton. Doing these will help your apps be smaller, quicker, and nicer. When in doubt, get your friend who can draw good to do your art, etc. Go for clarity, brevity, elegance, speed, and intuitive grouping/layout of your views.
    Good luck.
    Steve

    This is an interesting question. First let's define what we want to accomplish. The essence of object oriented design is object refinement. We want a system where we can extend the calculator functionality as our needs change. We start with a 4 function calculator and perhaps later add scientific functions or hex functions etc. We also want to take advantage of the object oriented nature of the system to allow as much functionality with the smallest, simplest code possible. So we define a class called calculator that contains a set of methods to implement a basic 4 function calculator. A lot this comes from an article in PIE developers from NewtonScript designer Walter Smith on creating classes with NewtonScript. That article alone makes it worth getting a copy of the magazine.
    calculator := { stack: 0, acc: 0, clear: nil, New: func() // this method is called from the clKeyboardView's { // setupDoneScript to create an instance of the class _parent: self, stack:0, acc: 0, clear: nil, }, add: func( view ) begin view:invalDisplay( stack + acc ); end,
    subtract: func( view ) begin view:invalDisplay( stack - acc ); end,
    multiply: // etc... divide: intDigit: func( digit, view ) begin if clear then begin acc := 0; clear := nil; end; acc := acc * 10 + digit; view:dirty(); end, };
    The next thing is to get our new instance called by our keyboard view. This is designed into the view class. After examining the documentation for the clKeyboardView it is apparent that nearly anything can be passed to the keyPressScript, including symbols. This is very convenient since it means that we can define new functions by simply attaching symbols to the table defining the keys on the keyboard. So now instead of having the keyResult from the clKeyboardView return a character we either get a symbol or an integer digit and it is passed on to the appropriate method from the calculator class.
    keyPressScript: func (key) begin if (classof(key) = 'int) then begin theCalculator:intDigit( key, theKeyboardView ); end else begin perform( theCalculator, key, [theKeyboardView] ); end; end; That's it, no case statements necessary. Now we have a base class that can be extended and new functions can be added to the calculator by extending the base class. The problem with the case statement is that it does nothing to keep the changes encapsulated. If you feel you need a case statement reexamine what you are doing for a more object oriented approach.     Compile


    Compile(string) compiles a string as a NewtonScript expression and returns a zero-argument function that evaluates the expression. Thus the usual way to use it is:
    call compile(string) with ()
    The usual reason for confusion is not realizing that Compile compiles _expressions_, not _functions_. The expression may consist entirely of a function constructor, but it's still an expression that has to be evaluated for the function construction to actually take place.
    I think this is documented better in the next NewtonScript manual. (At least, I hope it is.)

    Code stripping bug
    ******************
    Dan Keith, dbk@mcs.com writes:
    I found a bug in the NTK 1.0.1 NewtonScript compiler with regards to
    dead-code stripping and if-then statements.
    (If this looks familiar, it's because I got it from my message on the Newton Developer Talk board on AppleLink, 5/19/94...)
    This is a bug in the compiler's handling of IF statements with constant conditions. The bug occurs only if the result of the IF statement is not used. For example,
    func () begin if true then if true then print(1); print(2); end will trigger the bug, but func () begin local x := if true then if true then print(1); print(2); end will not. Thus, the workaround is to use the result of the IF statement. You don't really want to keep the result around, so the example above is not the thing to do. The easiest and most harmless workaround is probably the following: func () begin ( if true then if true then print(1); ) and true; print(2); end This works because the NTK 1.0.1 compiler is not smart enough to figure out it can throw away the "and true" part, but the result of the IF will be dropped immediately.
